# Continuous learning and customer-led growth

Implementation revision: 2026-10-19 UTC. This document describes executable code, its supported contracts and the remaining live bindings. The goal is better customer contribution and experience, followed by voluntary reinvestment. Wallet deposits, approval clicks and ad spend are not evidence of profitable outcomes.

## What is implemented

The persistent OS accepts prospectively registered randomized trials, revisioned outcome reports and customer feedback. Each accepted report runs a real Mastra workflow, updates the personal recommendation and transactionally replaces that organization's eligible shared contribution. Other opted-in organizations benefit on their next learning refresh. Enrolled workspaces refresh while their dashboards are closed through the existing worker. No new demonstration data is generated by refreshes.

| Module | Responsibility |
| --- | --- |
| `src/os/optimization-contracts.mjs` | Strict settings, trial, report and draft-receipt contracts |
| `src/os/optimization-state.mjs` | Immutable registration, corrections, versioned settings and exact draft approval |
| `src/os/optimization-learning.mjs` | Bounded shared prior, personal inference, conservative ROI floor and feedback veto |
| `src/os/optimization-workflow.mjs` | Mastra evaluation with deterministic statistical code |
| `src/os/repository.mjs` | Atomic workspace, cohort statistics, audit and receipt transactions |
| `src/os/job-worker.mjs` | Leased, retryable reporting jobs; every report step has a durable receipt |
| `src/os/adapters/campaign-draft-port.mjs` | Idempotent, organization-scoped managed draft handoff |
| `src/os/wallet-growth.mjs` | Voluntary funding preferences, snooze, unpaid intents and strict checkout receipts |
| `src/os/adapters/wallet-checkout-port.mjs` | Existing Wallet / Stripe Checkout adapter; no second financial ledger |
| `web/js/optimization-views.mjs` | Separate live/fixture evidence, explanations, controls and funding requests |

`npm run demo:optimization` exercises seven synthetic customers through the actual SQLite/D1 repository, leased queue, Mastra evaluation, draft port and unpaid funding intent. `fixtures/continuous-learning/verification.json` is the reproducible result, not real customer performance. The 100-customer workbook replay remains a separate fixture pipeline for attributed economics; it cannot retrospectively become randomized causal evidence.

## Producer contract and metric definitions

The initial scope is Search, USD and `qualified_conversion_v1`. Four strategy families rank research: creative proof, offer clarity, audience refinement and landing-page message. A common strategy label does not mean all creatives are interchangeable. The shared prior is a weak research signal, not a transportability claim.

The trusted producer must register a trial before enrollment starts, and wait for its registration commit before running it. The server rejects backdated registrations. Registration fixes organization, managed account, campaign, Brand/creative versions, control/candidate hashes, assignment unit, time window, maturation cutoff, sample target, reward bound and current budget. The entire design is immutable and addressed by SHA-256. Production must resolve these hashes to immutable source assets; hashes alone do not show that an asset is approved.

Both arms must reach the exact registered target, with 1:1 assignment to independent customers. `units` means independently assigned eligible customers, including zero-conversion customers. `qualified` is the count of those units with a deduplicated, mature qualified conversion, at most one per unit. Both arms use the same eligibility, qualification, attribution and refund windows. `contribution_sum_usd` is summed net customer contribution after returns, variable fulfillment costs, ad acquisition cost and platform fees, using pre-registered accounting rules. `acquisition_cost_usd` is a positive, reconciled source cost for computing net contribution / acquisition cost. Do not substitute gross revenue or ROAS for this field.

The producer verifies per-unit rewards fall within `[-contribution_bound_usd,+contribution_bound_usd]` and sets `bounds_verified` only when this holds. The API can validate the aggregate bound but cannot reconstruct per-unit evidence from a sum. Clipping after seeing the answer invalidates the interpretation; any clipping and treatment of outliers must be registered in advance, and results then apply to the bounded metric. Assignment, tracking and bound attestations must come from source-owned exposure/outcome records, never a browser checkbox. `assignment_verified` requires deduplication, independent units, correct assignment, no sample-ratio anomaly, no excluded unfavorable outcomes and no selective stopping. Maintain unit-level audit records in the source. The current code does not build a live serving/assignment service.

Non-overlapping trial windows are required per organization and mode. This prevents overlapping account tests in the pilot; it is not proof of independent customers. The source must still prevent reuse/dependence. Final reports are accepted only after maturation, with exactly the registered target in both arms. Insufficient traffic remains incomplete; it does not become a win by stopping early. Source reporting coverage or costs that cannot be reconciled must set a guardrail violation and hold adoption.

Every report references the exact design hash and a monotonically increasing source revision. Identical revision retries are harmless; changed content under the same revision conflicts. A correction replaces the active report rather than adding more observations. A negative correction can immediately remove eligibility. Report timestamps cannot move backwards or into the future. The latest registered trial for a strategy must itself qualify; a historical winner cannot override a pending or losing newer trial.

## Personal and shared learning

Each workspace has independent `fixture` and `live` contexts. Source mode is assigned by the authenticated producer, not inferred from uploaded spreadsheet values. The real adapter must reject fixture identifiers and be bound to verified Hellyeah organization membership. Setting `source_mode: live` is not a certification that numbers are real. No live connector is bound in this release.

Shared contributions require explicit participation and enabled learning. Opt-out removes the stored contribution in the same transaction as settings; paused contexts also stop contributing and consuming priors. A cohort matches industry, country, channel, currency and metric. The current workspace is excluded. At least five other workspaces are required. The identity adapter must map a real organization once; the pilot threshold is not proof of five independently owned businesses.

Each contributing workspace emits one pair of clipped quality counts (0–100) per strategy, regardless of spending or volume. Released mean rates are rounded to five percentage points. No financial totals, creative IDs, raw feedback or customer identifiers enter a pooled release. Pooled evidence contributes at most 20 pseudo-observations per arm; personal data takes over as it accumulates. This is a descriptive shrinkage estimate for ranking hypotheses. Selection bias and differences between businesses can remain.

Only mature, verified trials from the past 90 days contribute. An indexed cohort query excludes stale rows even if that workspace has not been refreshed. Existing model snapshots are historical records; opt-out affects future evaluations rather than rewriting prior audit evidence. Draft approval refreshes the cohort before comparing the input hash, so a new approval cannot rely silently on an old cohort state.

Thresholding, equal weights and rounding are not differential privacy. Before broad release, review differencing attacks and small-cohort leakage, strengthen canonical organization identity, and adopt a suitable privacy budget or fixed release policy. Do not claim formal anonymity.

## Adoption checks

The primary promotion evidence comes from the latest personal trial, not the network prior. For a bounded outcome with range R and n independent assigned units, the implementation uses a Hoeffding radius `R * sqrt(log(2 / alpha) / (2*n))`. A difference lower bound subtracts each arm's radius from the observed difference. For qualification R=1; for contribution R=2×the registered bound. The candidate ROI floor uses the lower bound of candidate contribution divided by reconciled acquisition cost, not the optimistic point estimate.

The error budget at evidence revision k is `0.05 * 6 / (pi² * k² * 4 strategies)`, split across the bounded component checks. Repeated evaluations of unchanged input do not create fresh evidence. Budgets are intentionally conservative; increasing evidence revisions can widen a threshold. These guarantees depend on the prospective fixed design, independence, valid bounded outcomes and truthful producer attestations. They do not survive biased assignment or invalid source accounting. A prototype calculation is not certification of a platform-wide causal policy effect.

The OS requires positive personal quality and contribution improvement lower bounds, the customer's conservative contribution ROI floor, a usable latest trial, enabled learning and no unresolved material customer concern. Low or ambiguous evidence returns `collect_evidence` or `hold_or_retest`. A new qualifying result returns `review_campaign_draft`. The model records its input hash, version, evidence revision, expiry, reasons and orchestration. It never self-reports a measured improvement factor.

Draft packets preserve the winning candidate, source snapshots and current budget. Requested budget equals existing budget, and `spend_authority` is false. The adapter can prepare a Draft only: it cannot reserve funds, submit a launch, turn on delivery or change a running campaign. Hellyeah's existing exact-plan validation and customer approval must still run before execution. Genuine autonomous delivery adjustments need a future explicitly scoped execution policy and source staging certification; they are not enabled here.

## API and integration recipe

The browser keeps owner-private Sites identity and same-origin checks. Joint deployment must replace the pilot identity resolver with Hellyeah organization roles. Trusted reporting uses `x-hy-service-key`, a verified `x-hy-workspace`, JSON and a stable `Idempotency-Key`. Do not expose that service key to a browser or use the Site access bypass as an ingestion identity.

1. Save `{kind: 'optimization_configure', payload: {expected_version: 0, config}}` through `POST /api/os`, with a config parsed by `optimizationConfig`.
2. Before the experiment starts, post `optimization_register` with a `trialDesign` payload to `/api/os`; registration can also use `/api/os/jobs`. Read back the stored `design_hash`. Delayed queued registration that misses the start time must fail; never backdate it.
3. Push `{kind: 'optimization_batch', payload: {reports: [...]}}` to `/api/os/jobs`. Each batch accepts 1–10 `trialReport` objects scoped to one workspace. HTTP 202 means accepted, not evaluated. Direct `optimization_report` is also service-only.
4. The worker processes ordered workspace jobs using stable operation keys. A partial batch resumes completed steps rather than counting them again. Source corrections use new revisions and stable design identity. The older `source_batch` cursor contract remains fixture-only and separate; these trial batches do not advance its account-report cursor. Your source connector must checkpoint durable acceptance and replay with stable keys, reconcile failed jobs and avoid unbounded out-of-order corrections.
5. The UI displays updated personal/shared recommendations. `optimization_propose` records an exact user-approved packet tied to `source_mode`, `strategy_id` and `input_hash`.
6. Bind the managed draft port server-side, then call `optimization_prepare_draft` with `{source_mode,proposal_id}`. The wrapper refreshes evidence, validates the approved plan, looks up prior provider operations, prepares a draft once and saves the receipt. A lost acknowledgement is recovered through provider lookup.

Hellyeah's public X-Ray collection endpoint is not the internal reporting API. Joint implementation must supply the protected reporting reader and reconcile persisted events; a collector's 200 response is not evidence that an event was saved. Official references: [X-Ray API](https://docs.hellyeahai.com/tracking/api-reference), [spend approvals](https://docs.hellyeahai.com/billing-safety/approvals), verified 2026-10-19.

Bind adapters in `app/api/os/[[...path]]/route.ts` when Hellyeah provides the implementations:

```js
return handleOS(request, {
  repository,
  serviceKey: env.HY_OS_SERVICE_KEY,
  draftPort: hellyeahManagedDrafts, // lookup(request), prepareDraft(request)
  checkoutPort: hellyeahWalletCheckout, // lookup(request), createCheckout(request)
});
```

These are semantic ports, not invented public Hellyeah URLs. Both lookup and creation must scope by canonical organization and operation ID, reject mode mixing, check source object ownership, honor source version preconditions and deduplicate concurrent calls in the provider. The HTTP handler exposes capability flags so the UI shows handoff controls only when the ports are bound. Failure to bind produces an explicit recoverable error, not a fake success. Source launch checks must revalidate the plan even if evidence changes during an in-flight draft preparation; a prepared draft carries no delivery authority.

## Customer experience and voluntary Wallet growth

The product tracks explanation feedback and material concerns separately from measured outcomes. A positive rating never changes revenue or trial counts. Suggestions are off by default; users can enable them or snooze for seven days. A proactive funding suggestion requires a current eligible **live personal** strategy and no unresolved negative customer feedback. Synthetic wins never trigger it. Suggestions contain no invented Wallet balance or automatically chosen amount: the customer checks the source Wallet and chooses the amount.

`wallet_intent` saves an explicitly confirmed amount in cents, currency and mode. It is bounded to $100–$100,000 and creates zero charge and zero credit. The placeholder `stripe_checkout_url` is `null`, with status `Awaiting checkout connection`. It is not a dead dummy payment link. A user may manually plan a top-up even when proactive suggestions are suppressed.

When the checkout port is bound, `wallet_prepare_checkout` uses the saved intent, not client-supplied pricing. The provider must create a Stripe session server-side for that exact organization, amount, currency and mode, verify customer membership, use approved return URLs, and disable adjustable quantities/discounts that change the confirmed amount. The receipt must match the intent and contain a non-expired HTTPS `checkout.stripe.com` URL, session ID, matching `livemode` flag and `payment_status: unpaid`. Lookup-before-create recovers a lost acknowledgement. A changed amount requires a new confirmed intent. An expired checkout requires a new review.

The existing Hellyeah Wallet service remains the financial system of record. Its verified Stripe webhook and reconciled ledger own successful payment credit, delayed payment failures, refunds and idempotent accounting. This OS does not mark a redirect as paid or implement a duplicate money ledger. Funded balance must be read back from the authoritative Wallet before reservation or launch. See [Stripe fulfillment](https://docs.stripe.com/checkout/fulfillment.md?payment-ui=stripe-hosted), verified 2026-10-19: fulfillment must verify payment and happen only once, including webhook retries. Swapping a literal link alone does not finish this integration.

## Verification and scaling boundary

Run `npm run quality`, `npm run demo:optimization` and the production build. New tests cover negative corrections, no double counting, cold starts, personal evidence overriding a positive network, mode/country isolation, consent withdrawal, fixed enrollment/maturity/bounds, late/overlapping designs, expiry, conservative ROI, feedback vetoes, source-only ingestion, durable queue execution, transaction rollback, HTTP draft handoff, lost provider acknowledgement, checkout amount/URL/status validation, unpaid funding and dashboard controls.

The pilot stores at most 60 registered trials, 50 draft packets and 50 funding intents per context/workspace, under the existing 1.5 MB response envelope. Shared statistics use indexed cohort lookups with one clipped contribution per workspace/mode/strategy; each workspace mutation is serialized by a fenced compare-and-swap transaction. This supports bounded pilots; it is not load-tested infrastructure for millions in spend. Normalize immutable trials/reports and funding intents into dedicated tables, add pagination/retention and signed source provenance, and benchmark realistic queue throughput before removing those limits. Retain the repository/port contracts so those migrations do not replace the decision engine.

Mastra's transient step metadata remains in memory. Durable D1 jobs and command receipts replay these short, deterministic evaluations after a crash. No external financial side effect occurs inside the workflow. Long suspended workflows require a persistent Mastra store before adoption.

To prove the network effect, prospectively randomize eligible organizations to personal-only versus bounded pooled recommendations, pre-register net contribution, experience/retention and harm guardrails, account for organization-level clustering, and evaluate on new cohorts and time periods. Report intent-to-treat effects and uncertainty; do not select only successful accounts. Wallet top-up conversion is a secondary product measure, never the optimizing reward or a substitute for customer profit. No real-world ROI lift or 2×–5× improvement has been demonstrated by these synthetic tests.
